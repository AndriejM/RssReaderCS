# Ревью `rss-content.tsx`

В целом код короткий и читаемый, хуки вызываются до условных return'ов (правила React соблюдены), `rel="noopener noreferrer"` на ссылке есть. Но есть несколько реальных проблем:

## 🔴 Критичные / архитектурные

**1. Синхронизация пропса в store через `useEffect` — антипаттерн «adjusting effects»**

```
useEffect(() => {
    updateRssId(props.rssId);
}, [props.rssId, updateRssId]);
```


Это вызывает лишний цикл рендеров: компонент рендерится со старым значением из store → effect обновляет store → повторный рендер. При быстрой смене `rssId` (например, в списке) возможна гонка: запрос для нового id стартует, а данные ещё отрисовываются от старого. Лучше вынести «выбранный rss» наружу — в URL-параметр (у вас есть `react-router-dom`) или держать выбор у родителя и передавать в store синхронно при рендере, а не в эффекте.

**2. `Suspense` и `ErrorBoundary` здесь мёртвый код**

Внутри нет ни одного ленивого/асинхронного компонента — данные приходят через `leo-query`, а не через React Suspense. Значит:
- fallback `<div>Loading...</div>` **никогда не покажется**;
- ошибки запроса (`getRssById`) обработает query-библиотека, а не `ErrorBoundary`.

Если библиотека даёт статус запроса (заголовок `useRssContentStoreAsync` на это намекает), то загрузка/ошибка должны читаться из состояния store и рендериться явно. Иначе у вас «ложная» обработка состояний: пока новый id грузится, компонент отрисует **старые** данные (`rss` ещё содержит предыдущий item) — без индикатора загрузки и без очистки.

## 🟡 Средние

**3. XSS-поверхность в `description`**

```
parse(DOMPurify.sanitize(rss?.itemPayload?.description || ""))
```


DOMPurify по умолчанию:
- разрешает `<img src>`, `<a href>` → **remote tracking / утечка IP** пользователя через картинки из RSS;
- сохраняет inline `style` (CSS-инъекция всё ещё возможна).

Для не-доверенного контента из RSS стоит передать конфиг: например, запретить/фильтровать теги с сетевыми эффектами, или хотя бы явно прописать `ALLOWED_TAGS`. Минимум — осознанно зафиксировать текущее поведение.

**4. Запрос не «привязан» к отображаемому id**

При смене `props.rssId` до прихода ответа показывается контент **предыдущего** RSS (stale-while-revalidate без указания). Варианты:
- рендерить заголовок/ссылку только если `rss` соответствует текущему `props.rssId` (хранить id вместе с item или сравнивать);
- либо сбрасывать данные при смене id в store.

## 🟢 Мелочи

- **Hardcoded-строки** (`"No RSS selected"`, `"Loading..."`, `"Error loading ..."`, `"Link not available"`, `"No description available"`) — вынести в константы/словарь, особенно если появится i18n.
- **`RssLink`**: текст ссылки — «сырой» URL. Обычно показывают `rss.title` или заголовок payload'а, а URL остаётся в `href`.
- **`<div>No RSS selected>`** и прочие fallback'ы — семантически нейтрально, но стоит подумать про `role="status"`/aria-live для скринридеров при смене состояния.
- **`useMemo([rss])`** корректен, но можно сузить зависимость до `rss?.itemPayload?.description`, чтобы не пересанитизировать HTML при изменениях полей, которые не используются.
- Тип `RssContentProps` экспортируется, но используется только локально — ок, но следите за согласованностью стиля (в проекте смешаны single/double quotes — у вас в файле double, а в `button.tsx`/store'ах single).

## Итог

Главное: убрать иллюзию Suspense/ErrorBoundary и завязать отображение данных на **текущий** `rssId` (loading/stale-state), плюс решить вопрос с синхронизацией пропса в store. Остальное — улучшения безопасности рендера HTML и UX-детали.
